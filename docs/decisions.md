# Decisions

What the code alone does not tell: the owner's decisions with their reasons, invariants of stored
data, and rules a change must keep. Read the section of the area you touch before changing it.

One line per decision. When the owner decides something the code cannot show, add a line here in the
same commit. When a decision changes, change its line; when it no longer holds, delete it. How each
area is built is in its `CLAUDE.md`; work not built yet is in `docs/plan.md`.

## Product and scope

- SprachAnker is local-first and private: all learner data stays on the user's machine, no telemetry, no accounts, no cloud service.
- Non-goals: a cloud service or accounts, app-store distribution, courses generated by an LLM, strong multi-user security, gamification that punishes (streak loss, hearts).
- Real courses first, LLM second: the curriculum comes from courses; the LLM checks, explains and converses inside it, never invents or rewrites course content.
- Primary users: a Russian-speaking adult in Germany learning German from A1, plus a second household profile; iPhones as clients, a Mac as server.
- The app is language-pair agnostic: German/Russian is the first pair, and nothing in the domain or code may assume German or Russian.
- A profile keeps no languages of its own (owner, 2026-10-10): what it learns is the courses it takes; UI language is independent of course languages.
- Constraints: macOS on Apple Silicon first, Windows and Linux supported by design; iOS microphone in a PWA needs a secure context (HTTPS).
- Success measure for extensibility: a new course source needs only a new provider folder, no engine or UI changes except new exercise types.

## Course content and the law

- Closed-licence content (e.g. DW) is downloaded by the user, for personal use, on demand, from the source to the user's machine; nothing is hosted or redistributed by us.
- No access control or DRM is ever circumvented; paid or locked material (e.g. Lingust's locked players) is skipped.
- The repository and release artifacts contain code and lists of public URLs only, never third-party texts, media, raw pages or PDFs.
- Source logos and brands are never used as SprachAnker branding; a source appears only as attribution (publisher, URL, licence shown with the course).
- Deutsch im Blick: only the 2nd edition (2017, CC BY 4.0) may be used; the 2013 edition is CC BY-NC-ND and MUST NOT be imported.
- Every text in the library is the source's: a provider invents none (an untitled page stays untitled; the app names it by its kind).
- German-only sources (Leben in Deutschland, Goethe) are shown as they are; no translation is made, because content is never generated.
- Our corrections of source errors (DW `corrections.json`) are hand-written, hold no more of the source than the replaced phrase, and apply only while that phrase is still present.
- Enrichment is hand-written and reviewed, never LLM-generated, references keys and fingerprints only, never copies third-party text; an entry whose fingerprint differs is stale and skipped.
- An exam's sources file exists as proof that the data is the source's (owner, 2026-10-10): documents, copy hashes, checks run, each question's place.
- Leben in Deutschland keeps a question only where the PDF and the test centre list the same options word for word; disagreement leaves it out and reports it.

## Library, keys and providers

- The library holds only downloaded content and data derived from it: no learner data, no enrichment. Each series folder is self-contained; restore = copy the folder.
- The library stays unpacked on disk (served per file with ranges, normalised and backed up per file); bundles are only for moving a course.
- Target-language strings live in canonical files, learner-language strings in locale files at the same key path, so adding an edition never changes canonical files.
- Where an edition's two languages share a script, an ambiguous text stays canonical: guessing could move German text into the locale.
- Fingerprint = sha256 of the exercise's canonical JCS without `fingerprint`; it must stay identical across editions of the same content (enrichment and staleness depend on it).
- Normalised output is deterministic: same raw input and same provider version give byte-identical files (NFC, sorted keys, pretty-printed).
- Content file formats carry an integer `format`, bumped only on breaking change; importer state (`media.json`, `keys.json`) has none and an unreadable one stops the import.
- An invalid library file is an error, never partially used; a normaliser still writes a failing file, but the import counts it and ends with an error.
- Media files no URL points to any more stay on disk, because past runs and cards may still name them.
- `newWords` and `ruleIds` stay in the format although providers write them empty: every stored library file and page snapshot holds them, and schemas are strict.
- Every `ruleIds` value anywhere must exist in `courses/_shared/rules/<lang>.yaml`, the only place rules are defined.
- A `classify` exercise type is added only with the first source that needs it; no current source has a categorisation mechanic.
- Keys follow the source's own order and numbering (where it numbers tasks, that number), so a normaliser fix that maps one more task never moves the others.
- After the first normalisation a key stays with its source id via `keys.json`: inserts or drops shift nothing, a removed number is never re-used.
- An unreadable key map stops the normaliser: numbering afresh would hand kept keys (and learner progress) to other content.
- Lexeme part of speech and gender come from what the source states, never guessed; otherwise every provider uses `shapeHeadword`, so one entry is one lexeme in every course.
- A card follows its vocab key (lesson + lemma): a lemma corrected at the source is another word, and the old card keeps its progress.
- A language pair of a source course is a separate course (DW `a1-ru`, `a1-en`): the source publishes them separately and they differ. Editions only for true translations.
- Ready for learning: DW Nicos Weg, Leben in Deutschland and Goethe A1 (owner, 2026-10-10; A1 2026-10-12); every other course is experimental, shown only when its source is enabled in Settings.
- Every provider's courses are offered in Courses → Available, unfiltered until the learner narrows them; nothing sets a filter for them (owner, 2026-10-08, 2026-10-10).
- A medium the source answers 404/410 for is "not at the source": reported, retried next run, but it never leaves the course incomplete.
- Removing a course is never blocked, even mid-lesson (owner, 2026-10-12): the only alternative would delete learner data; its runs wait (409 `course_gone`) until it returns.
- Removal keeps `keys.json`, so a course downloaded again gets the same keys and the learner's runs, cards and Notebook meet it.
- Bundle defaults are the owner's, changeable (owner, 2026-10-11): `raw/` left out except exam source copies; a differing course is replaced, not asked.
- A bundle is data only, never executed; it replaces nothing but its own course's folders, and a same-named file with other content stops the install — except a picture the importer made (its media address has a fragment: a part of a fetched document, Leben in Deutschland's PDF) brought with other bytes under the same address and name: another version made it, ours is kept and the bundle installs (owner, 2026-10-16).
- A bundle holds courses of one series; courses sharing most of their media (a course in several languages, its videos the same) go in one bundle, a few shared files may be in two. Version 1 bundles (one course) are no longer read: no release had them.
- A bundle moves by one path on every system, the phone too (owner, 2026-10-16): exported as a stream straight from the library — only what an import rewrites in place (library JSON, exam source copies: small) linked or copied aside as it is made ready; media and recordings read where they are as it downloads, one changed since fails it — and imported as it comes, what the library lacks written as it passes: no copy of the course, no room beyond the file. The library keeps its folders, not a zip per course: a series shares media across courses, practice and media are added over time, and removing a course would rewrite gigabytes.

## Lessons and scoring

- A lesson's score is the mean first-attempt score of its scored items; retries are recorded and shown but never improve the score or statistics.
- Skipping a checked item before answering it is its first attempt: it scores 0 and marks the exercise wrong ("skipping what is checked is not knowing it"); a later answer does not count. Skipping an unscored item costs nothing.
- A lesson is completed when every plan step is done or skipped; any step may be skipped. A words-only lesson is done without a score.
- A `finished/completed` run stays a completion forever: a lesson changed later (an exercise added on re-normalising) never takes it back.
- A lesson never depends on an assistant: AI steps join the plan only while one is set up, and the server does not require them to finish a run (`run_incomplete` covers exercises and reading steps only).
- Results are binary except multi-select, `order` with a correct prefix, and dictation/speech with at least 80% of words matched (counted against the longer of reference and answer).
- Answers match by ids, never display position; options with identical content (text as written, only whitespace evened) are interchangeable, so "Berlin?" and "Berlin." differ.
- Closed exercises' answers are visible to the client; accepted for self-study, so no effort goes into hiding them.
- Opening a lesson starts no run (owner, 2026-10-07): a run starts on "Start" or on opening a page; the step is in the address (`?step=`) so a reload stays on it.
- One active run per (profile, context) and one active review run per profile; Tutor-section chats are the exception, each active until deleted. Switching a course's edition abandons its active lesson run.

## AI practice

- AI practice stays out of the lesson's score and its mistakes list; each AI step gets a mark from its first work in the run, like an exercise's first attempt (owner, 2026-10-12).
- An AI step's main button is Check until the step is done, never Next; Skip passes it by (owner, 2026-10-12).
- The Speaking step is switched by the AI place key `scene` (kept from the Dialogue it replaced); the place `speaking` is the AI's check of spoken answers. That check is asked by itself as an answer is heard, once for the same words, with no button (owner, 2026-10-15).
- Going over mistakes is in the summary, not a plan step (owner, 2026-10-12): a lesson's few mistakes, mostly slips, made a long lesson longer. Offered only while `hasMistakesToGoOver`.
- Going over mistakes is structured, never a chat (owner, 2026-10-12): a chat dumped every mistake at once and missed one inside a long gap item.
- Going over mistakes makes one model call per mistake type, side by side: a single call for all took up to three minutes.
- A difference only in accents or umlauts is another word, not a spelling slip (owner, 2026-10-12): Mutter/Mütter, schon/schön, si/sí differ in meaning or form.
- Mistake groups put grammar first, then pairs, then options chosen: options in courses mostly test film comprehension and crowded out grammar points.
- Answers said aloud and comprehension questions are listed only, with no new items: mostly recogniser mishearing, and a comprehension slip is no grammar point.
- Speaking replaces the Dialogue (owner, 2026-10-12): no waiting for the model after every line; a monologue card or role-play is said aloud and checked once at the end.
- Every lesson task gets the knowledge snapshot; no task may assume A1 or a beginner.
- AI practice belongs to courses only, not exams: an exam's parts are the exam's own.
- Every practice text comes from one generator: Reading, Listening, the message Writing answers, and Speaking's role-play (owner, 2026-10-12).
- Code, not the model, draws the genre and the areas of life, so texts vary across lessons.
- Three drafts are written side by side and a judge rates them. The best passing draft is kept; otherwise one is rewritten with the judge's problems. The reason: single drafts did not hang together (owner, 2026-10-12). When more than one text is wanted (practice made 2–3 at a time), the other drafts that pass are kept too, best first: one round for several texts (owner, 2026-10-14).
- A lesson's AI practice is made once into the course, not per profile (owner, 2026-10-14): it is stored in the library with the course, carried in its bundle and merged on import, and kept when the course is removed. A step takes the next variant the profile has not had, without a model, so a course is studied offline on a phone with only checking online.
- One variant of each step by default. More are made into the course, 1–3 at a time, from the course page for every lesson and by `sprachanker practice`; both run the same job (owner, 2026-10-14). They fill each lesson's steps up to that many, so a job started again goes on where it stopped. A course's job makes three units at a time (one on LM Studio, which answers one call at a time). A lesson makes no practice: no making button or count in its steps (owner, 2026-10-15).
- The practice is recorded with Qwen3-TTS only: Listening's texts and a role-play partner's lines. Without Qwen3-TTS, Listening is not made, and Speaking makes only monologue cards (owner, 2026-10-14).
- As a lesson starts, each step whose latest work is done takes its next variant the learner has not had (an untouched or half-done one stays theirs to finish); "Another version" in the step takes the next one at once, without a model, and is not shown when none is left. All had: the last one stays. A step is not in the lesson's plan until the course's practice has it (owner, 2026-10-15).
- The course page's AI practice opens from a button among the course's actions (beside syncing and resetting progress), shown only while open; the button says how far a job is (owner, 2026-10-15).

## AI assistant

- The app has no LLM runtime of its own and stores no models. Local models run in LM Studio; cloud models use the user's key or a CLI subscription.
- One route (provider and model) per profile serves every task. Per-task routes are deferred on purpose.
- Command-line agents run in an empty folder with no tools, MCP, settings or saved session, so only the lesson context leaves the machine. Codex's sandbox can still read files, so recommend Claude Code where that matters.
- CLI effort is `low` only for short checks. Teaching replies and conversations keep the default, because low effort made replies drift (owner, 2026-10-12, a Sonnet walkthrough). The checks of Writing and Speaking (monologue, role-play) run without thinking: the learner waits for them, and Claude spent two thirds of their 30 s thinking; without it 13 s, the corrections alike on six texts (owner, 2026-10-15). So does the selection bar's Translate, which the learner waits for too (owner, 2026-10-15).
- An API key never reaches another origin: requests follow no redirect, and an endpoint URL with a login in it is refused (the key goes in the sealed key field).
- Tasks that answer the learner live (explanations, tutor, turns) ask for no reasoning phase, because speed matters more there. Gemini is the exception, since it refuses this.
- If a provider may use what is sent (Gemini's free tier), its settings card says so. User data goes only to providers the user configured.
- Structured calls outlive the page. They run to the end on the server and are stored, and a reopened page polls and shows the running step. Only one runs per lesson (409 `*_busy`).
- A streamed reply is stored only when it finished or the learner stopped it. A reply that breaks off shows the partial text with the error, never as a complete reply.
- Wherever the AI answers, the UI names it as "provider · model" in plain text. It is not a link, so a tap never takes the learner out of a lesson.
- The prompt viewer (`{}`) hides what the learner must not see yet, such as a running Dialogue's partner facts ("hidden until the end").
- AI places can be switched off one by one (owner, 2026-10-09). A place that is off disappears completely: its button, lesson step, section and nav entry. Lessons already done stay done.
- The AI never checks closed answers. The engine checks every closed item, including the ones a model makes. Models only set items and judge open text or speech.
- Model-made closed items are answered again blind by the model. An item answered otherwise or ambiguously is dropped, and for Understanding so is one answered right without the text. Every kept item has one settled answer.
- No task assumes A1 or "a beginner". The level comes from the course id (`levelOf`), not from a course-data field, because providers' ids already state it (owner, 2026-10-11).
- Target-language output stays within the words the learner knows by that lesson. A word they have not met gets a translation or gloss.
- A person a task invents (Dialogue partner, people in a text) is never one of the course's characters.
- The learner's gender is unknown. Learner-facing wording must not mark it, and must not show both forms side by side ("смог(ла)").
- Prompt rules alone did not keep wording gender-neutral. JSON replies are also checked in code (ru, uk, pl) and asked again once, and the safe Russian/Ukrainian rewrite is made in code first. The rules sit in the fixed suffix, so they survive learner-written prompts.
- Checks never correct what is already correct and never swap one correct form for another. A "corrected text" changes only the listed corrections.
- Corrections are capped (writing three kept, a talk or Dialogue line two), most important first, so feedback never becomes a pile.
- An AI verdict on a spoken answer makes the item a lesson mistake for going over and for the tutor. It never counts in the lesson score (owner, 2026-10-08).
- The lesson tutor handles questions and explanations only, because practice is the lesson's steps. Hints come first only for the exercise on screen; any other question is answered at once.
- Both tutors treat real-life language (slang, swearing, insults) as in scope. They explain it plainly and never refuse because it is not in a course (owner, 2026-10-11).
- In a Dialogue, the app ends the conversation when every goal is met, and a model's own `done` is ignored. The partner never asks the goal question or gives a fact before it is asked.

## Speech

- The language is always explicit, for recognition and reading aloud; never auto-detected. A text that mixes languages is never read aloud (owner, 2026-10-11).
- The reference text is never sent to the recogniser, because it biases results. It may only filter silence after hearing (`expect`) and diff the transcript.
- What the recogniser hears is taken as is, normalisation included (punctuation, capitals, digits), and a heard line is never edited: it is what a listener would understand (owner, 2026-10-11).
- Speech results are practice feedback, not pronunciation grading. The recogniser autocorrects errors, so the UI shows "Heard: …" literally.
- A spoken check never counts in a score: a lesson scores the same with recognition on or off; a self-rated speaking item counts once recorded (owner, 2026-10-08).
- Recordings are always kept (owner, 2026-10-11); only a take in which nothing was heard is deleted, and never while an answer holds it.
- "Recording" shows only once the microphone gives sound (owner, 2026-10-12): a device just opened gives exact silence for a second and more, and the first word said into it was lost; until then the button says the microphone is starting.
- The browser's microphone processing (gain, noise suppression, echo cancellation) stays off: it reshaped the voice and Whisper misheard. A take starting stops all playback.
- Whisper invents words for silence and noise. Its `no_speech_prob` is 0 for silence and its VAD needs another model, so neither is used: `silence.ts` filters by loudness and log probability.
- Low confidence alone never drops a transcript: a learner's accent makes Whisper less sure of a real answer (owner, 2026-10-12).
- Dictation only where the answer is to be said, in the language learnt. Never where the task is writing: free answers, the tutor, Writing (owner, 2026-10-11).
- Course audio is used whenever it exists; reading aloud is for text without audio, mostly the AI's, and mainly for listening (owner, 2026-10-08, 2026-10-11).
- A line is read on request only, never on opening. Exception: where the exercise is held by voice, a new partner line is read as it arrives (owner, 2026-10-11).
- Each person in a generated text gets a server voice of their gender (and age where known), at random, no voice twice (owner, 2026-10-12: same voices, women read by men).
- Read engines (owner, 2026-10-08/09): Piper and Qwen3-TTS run by us like Whisper; the device's voices read what neither can.
- Settings offer every engine — the device's voices, Piper, Qwen3-TTS — on every system, and the learner chooses (owner, 2026-10-16; the Qwen3-TTS-alone choice of 2026-10-14 undone). Qwen3-TTS is the default engine; where the chosen engine cannot read a language — not downloaded, a language it lacks — the device's voices read. Defaults suit the device: on a phone the small models (Whisper small, Qwen3-TTS 0.6B), every model offered.
- Words — a deck's words read aloud, Finds, words selected — are read by Qwen3-TTS's Base model in a native voice cloned from a recording of an installed course in their language (one speaker's sentence, its exact text from the course), in a process of its own beside practice's model; AI practice keeps the named speakers. Measured on 20 German words: the default speaker got 8 right and ran on with babble for up to 33 s on 11; the cloned voice 20 of 20. Piper is no answer (owner, 2026-10-15). Every Qwen3-TTS reading is capped in proportion to its text. The recording stays in the data root, never in the repository.

## Review

- Review is Anki one-to-one (owner, 2026-10-07): queue, limits, ratings, keys and actions behave as Anki's v3 scheduler with FSRS, so habits and imported decks carry over.
- Learning steps, the 4 AM day start and new cards counting against the review limit are Anki defaults and deliberately not settings (owner, 2026-10-11).
- One card per lexeme and translation language (owner, 2026-10-07): a word learned through Russian and through English is two notes, each showing its own translation.
- A card shows the word as the deck being studied gives it, else as made (owner, 2026-10-11): a course word once showed an imported deck's headword and audio.
- A real recording beats none (owner, 2026-10-12): a headword without audio takes the course's first recording of it, or the card's own, before any reading aloud.
- A card's word is never read aloud on the fly: its audio is its own or a reading made ahead for its deck.
- The lesson's "Words" step skips the daily new limit (the learner chose to learn now) but is otherwise Anki's reviewer; it is done once nothing is due now.
- Undo takes back only answers in the deck being studied: a lesson's Words step never undoes the morning's review.
- Leaving a deck removes its cards with their progress, after asking; a card whose word another of the learner's decks has moves there instead.
- Review → Decks shows each deck once (owner, 2026-10-15): its row has the day's counts, Study and a menu (more new today, leave, export to a file, delete an imported one), how many of its words are cards with the rest to add, and how its audio and examples stand in a line that opens what makes them; "Decks to take" lists only decks none of whose words are cards. The long explanation lives in "How it works".
- An imported deck is deleted only while no profile has cards from it: nobody's progress goes unasked. Removing made audio never touches recordings a deck or course brought.

## Exams

- A mock exam checks nothing before hand-in, and a running one's outcomes appear nowhere (run, stats, readiness) until it is handed in.
- An exam run's plan freezes each question's section and the questions as shown, so it scores the same whatever the catalogue becomes.
- An assistant's rating of an open answer is a proposal and scores nothing until taken as `exam_rated`; the latest rating counts and rescores a handed-in run.
- An exam's tasks are always the source's own (the Modellsatz): the AI never invents an exam task. It acts as the examiner — finds the mistakes, rates by the official criteria (a proposal), shows a model answer (owner, 2026-10-12).
- An exam is for being tested as in the real one; practice belongs to the courses. No weak-spot training or live partner in exams; a live conversation belongs to the Tutor (owner, 2026-10-12).
- Every exam (Goethe, Leben in Deutschland) runs on one exam layer and player: a change there reaches all of them.
- An exam's speaking part runs from a script written once from the Teil's cards (the examiner's fixed lines, the partner's from their card, the learner's places): no live partner and no wait for the model between lines; hints only in practice; rated once at the end by the official criteria, pronunciation by the learner from their takes (owner, 2026-10-12).
- Exam practice behaves as a lesson: an answer waits for Check in the step bar, then Next; Skip passes a question by. A mock exam keeps Next, since nothing is checked before hand-in (owner, 2026-10-12).

## Stored data, events and statistics

- Statistics are pure engine functions over events and cards; no derived tables unless a measured query is too slow, and then rebuildable from events. Study days are never stored; they use the server machine's time zone.
- Time spent (owner, 2026-10-07) is read from one timeline across all runs, so parallel runs count each pause once; a card answer counts at most one minute (Anki's maximum).
- A removed course counts none of its lessons as done, while its runs stay in the journal.
- What a run is (owner, 2026-10-07): a lesson pass, a review day, or one conversation; a one-off model verdict is an `llm_verdict` event in the lesson run it was given in, never a run.
- An event id is a client-generated ULID and the idempotency key; `ts`, outcome and attempt number are assigned by the server.
- Deleting a recording removes the file only; the event keeps its name and the UI shows "deleted".
- Resetting progress (owner, 2026-10-07) deletes every run of the course or lesson and the cards first met there; cards made by another lesson stay; the course stays installed.
- Legacy values must keep reading: `step_done` `understanding`, `scene`, `mistakes`; `llm_verdict` `example`, `dialogue`; `scene` runs. Old per-card examples and Dialogue runs are still read.
- Stored JSON columns of runs (plan, result) only grow, like payloads, on record in `packages/schema/test/stored-runs/`.
- Snapshots keep old runs readable after content changes or course removal; cards keep working from `display_cache_json`.
- `card_state` is written in the same transaction as its `card_review` or `card_undo` and must stay recomputable from those events.
- Migrations may be squashed into `0000_init` only until the first release; after a release, never.
- One profile is one folder (backup, move, delete are folder operations); the library never holds learner data, profiles never hold course content. The one exception: a profile's own deck (Finds) is a deck folder in `decks/` like any deck, owned by the profile, so that every deck is exported alike (owner, 2026-10-15); it goes when the profile goes.
- A deck file (`.sprachanker-deck`, owner, 2026-10-15) holds one deck's folder: deck.json (an imported deck, Finds), extras.json and the media they name; a course's holds only its extras, since its words come with the course. Imported, it is merged into the deck there by lexeme: the words, readings and examples (each language's) there stay, what is missing is added, a media file there is never replaced. An imported deck joins the deck there most of whose notes it shares in its languages (as an .apkg update finds it), else the deck of its id in its languages, else it is a new deck (numbered beside one of its id in other languages). A deck whose jobs are working is not imported into (`deck_job_running`); the file waits to be imported again.
- A Finds deck imported becomes the importing profile's own Finds of its language pair; only the words it adds become that profile's cards (a word whose card the learner left stays without one), and its cards that named the deck as it was (from a profile file) follow it, each to its word's key here. Only its owner exports it.
- What was made for a course's words (`decks/course~…`: audio read aloud, AI examples) is kept when the course is removed, as its AI practice is (owner, 2026-10-15): it waits for the course, as extras imported from a deck file before the course is installed do. Nothing writes into it while the course is not installed, but such an import.
- Backups keep what cannot be fetched again: `server.sqlite`, `profiles/`, `decks/`, `secret.key`; library, `models/`, `cache/` are disposable (owner, 2026-10-11). `secret.key` stays in app-data, outside the data root.
- A profile's daily copies live in its folder, so deleting the profile leaves nothing of the person behind.
- A profile file is for one's own machines only, and importing always makes a new profile, never replacing one (owner, 2026-10-11).
- The app on every system — macOS, Windows, Linux, Android, iOS — is complete and the same in features, through the same code (owner, 2026-10-15): a part is switched off on a system only where it truly cannot be built there, measured, with the reason said in the app — never because it was easier. So the phone app stands alone: one installs only it, and it downloads courses from their publishers, Whisper's models with the computer's choice, takes and gives files (courses, decks, .apkg, profiles), all by the server's own code over the phone's files.
- A file exported on the phone goes into its Downloads (MediaStore), the name as made; a file is taken through the system's picker. A download or a large transfer runs as a foreground service (a notification), so it goes on while the app is put away; the system may still end it (memory, the learner closing the app): a course's download then resumes at the next start, a transfer is made again.
- No engine is switched off on a phone because a phone is slow (owner, 2026-10-16: many are far stronger than the test phone): every engine and model is offered, what runs depends on the device, and slowness is said in a hint, never a reason to hide. Measured on the POCO X3 Pro (Snapdragon 860, 6 GB, CPU; 2026-10-16): Piper 1.7–2.2 s a text; Qwen3-TTS 0.6B 8–16 s a word or a sentence in the app (a computer: about a second), 2.7–2.9 GB, about 4 s to load; the Base word voice 16–20 s a word, 3.0–3.2 GB — the two did not fit beside each other in 6 GB (the app was killed), so a phone runs one Qwen3-TTS process at a time; the device's voices at once. ggml's Vulkan backend needs Vulkan 1.2 and 16-bit storage buffers; the Adreno 640 has no 16-bit storage buffers under Qualcomm's driver (Vulkan 1.1, Android 11 and 15) nor under Mesa's Turnip (Vulkan 1.3, loaded without root; measured 2026-10-18, Android 15: the CPU 7–11 s a word with the screen on, 60–90 s with it off — the phone sleeps), so no GPU build runs on it and the phone build is the CPU's — a GPU build ships only once it is measured faster and stable on a phone it runs on. Making a course's practice is offered on the phone as on a computer.
- The device's voices on Android are Android's TextToSpeech as the page's speechSynthesis, installed voices only: a language set without one is read by Google's server, which would send the text away (rule 5).
- The phone app is native — Tauri 2 with whisper.cpp in its process —, not the PWA (owner, 2026-10-14, measured with `speech:phone` and `speech:android`): Whisper in a phone's browser was too slow and wrong on Android (base 3–14 s, small up to 85 s) and did not load base on iOS (WebKit's memory limit); whisper.cpp itself on a Snapdragon 860 heard small q8_0 in 4–9 s with 98 % of the words.
- Whisper on Android: q8_0 models (ARM's int8 paths: 1.5–3 times q5_1's speed, the same words; q4_0 loses words), as many threads as big cores (the little ones slow every thread), always the whole 30-second window (one fitted to the answer lost half the words and looped).
- Profiles sync through the Mac's server (owner, 2026-10-14): the phone app keeps its own copy of a profile and, when the server is reachable (home network or tailnet), sends its new events and takes the others' since its last sync; the server's copy is the main one. On the phone the learner sets the server's address and which of its profiles this one syncs with. The browser app (PWA) works on the server itself and needs no sync.
- Two devices with an active run of the same lesson after a sync: the newer one (by its latest event) stays active, the other ends `abandoned`.
- Before the phone app: card ids derived from their natural key, deletions (progress reset, a chat deleted, a deck left) kept as events, events numbered in the order the server got them, settings with the time they changed — so a sync merges without guessing.

## Server, security and devices

- Threat model: a home network or tailnet of trusted people. Guard against accidental exposure and common web attacks, not a determined attacker on the LAN.
- Profiles are separation, not security (owner, 2026-10-07): every profile is equal, no owner or admin screens; server matters belong to the `sprachanker profiles` command.
- No PINs, passwords or passkeys (owner, 2026-10-08): profiles keep people's learning apart, and a home server needs no lock. A profile opens when chosen.
- A device session is a random 256-bit token in an HttpOnly cookie, stored as SHA-256. Not a JWT: one server decides, and signing a device out is deleting a row.
- The Host check exists against DNS rebinding: only this machine's own names pass, else 421. Never accept any `*.ts.net`: another tailnet's name could be rebound to this server.
- No CORS, same-origin only. Every mutating request needs the header `X-SprachAnker: 1` (CSRF guard); cookies are `SameSite=Strict`.
- `X-Forwarded-Proto: https` is believed only for the tailnet name and `--allow-host` names (our proxies), never for a name reached directly. It makes the cookie `Secure`.
- The CSP loads everything from this server only, no inline scripts, `frame-ancestors 'none'`, `no-referrer`: model output can never make the browser send data to another host.
- The phone app's WebView is the app's alone (owner, 2026-10-16): only its own pages (a link out goes nowhere), a CSP of what the app needs — its scheme, the media scheme, blob:, data: pictures, WebAssembly, Tauri's IPC; no frame, no other host: the server's code reaches hosts through the native side —, and the native bridge answering only while the app's own page is in the main frame. Android 11 (API 30) is the oldest it runs on: the owner's oldest device.
- Course HTML is sanitised at normalisation; Markdown renders without raw HTML; a course's or exam's links are http(s) only, so a course bundle never brings a `javascript:` link.
- API keys never travel in a profile file: they are emptied from its copy of the database, and the export says which it left out.
- LLM calls: course text and learner input go as delimited data; output is validated against schemas and never executed.
- No telemetry. Errors in the UI always offer an action ("Try again", "Open settings"), never a raw stack trace.
- CLI profile, course and backup commands stay safe while a server runs on the same data root: databases copied with `VACUUM INTO`, course changes under the series' import lock.
- The server listens on `127.0.0.1:4580` by default. Phones use `tailscale serve` (HTTPS on the tailnet name, proxied to localhost): a secure context for the microphone, the server still on loopback.
- `tailscale serve` needs MagicDNS and HTTPS certificates on the tailnet; its syntax changes between Tailscale versions, so check `tailscale serve --help`.
- Never `tailscale funnel`: it opens the name to the internet and profiles have no lock. While Funnel is on, the server refuses the tailnet name (421) and any `Tailscale-Funnel-Request`.
- Plain HTTP on the LAN (`--host 0.0.0.0`) is allowed but is no secure context: no microphone, and the UI says why.
- `/api/addresses` shows anyone who reaches the server its local IPs, `.local` name, tailnet name and serve/Funnel state. Accepted: the network already shows that.
- The PWA is installable but has no offline use: a failed request shows its error with "Try again"; a lesson's unsent events stay in memory and are sent again.
- The version is MAJOR.MINOR.N (owner, 2026-10-15): MAJOR.MINOR written in `apps/cli/package.json`, N the commit count of the build (`git rev-list --count HEAD`), so every build says which it is; the binary, the desktop app, the phone app (Android's build number: N) and a release's tag all carry it.
- Installing (owner, 2026-10-12): Macs with Apple Silicon, macOS 13 and later, only for now. The speech engines are built apart (owner, 2026-10-13: they change rarely): each kept as a pre-release of its own on GitHub, built by the Engines workflow only when its pinned version or the build script changes. A tag `vX.Y.N` builds the release on GitHub Actions (`macos-15`): the binary with those engines, the e2e on that build, an archive and `install.sh` as a draft release. `install.sh` (`curl … | bash`: no quarantine, no Gatekeeper prompt) puts the program in `~/SprachAnker/bin` beside the data in `~/SprachAnker`, keeps it running by a LaunchAgent on `127.0.0.1:4580`, and backs the data up into `~/SprachAnker-backups` before an update (a backup never goes inside the data folder). Running it again updates.
- The desktop app (owner, 2026-10-15): a Tauri window around the server it bundles with the engines — the same server, every feature, no second copy of its logic (the phone's way is for phones). The app is the server: it starts at login, its closed window leaves it in the tray, and it takes over the installer's LaunchAgent for the same folder, keeping its port and address; else it serves `~/SprachAnker` on port 4580 on all addresses, so phones reach it as before. macOS first, Windows and Linux after. A `.app` with everything inside, a zip and a dmg in each GitHub release, signed ad hoc — no Developer ID: Gatekeeper asks for each new version (Privacy & Security → Open Anyway), and macOS asks for the microphone again. `install.sh` stays for a server without a window.
- Third-party notices ship in every build (owner, 2026-10-16), so the app may be given to others: one file, `THIRD_PARTY_NOTICES.txt` — every component with its version, licence, copyright, exact source and the builds it is in, then the licence texts — made from the lockfiles and a hand-kept inventory of what the engines link (`scripts/notices`); beside the program in the archive, in the Mac app's Resources, in the APK's assets, and opened from Settings → About on every system. Models and voices the app downloads are listed there with their licences and links, not shipped. `sherpa-onnx-offline-tts` links eSpeak NG (GPL-3.0-or-later): a separate program under the GPL, its sources linked at their exact versions (owner, 2026-10-18: links to the sources, no written offer); the program's Bun links LGPL JavaScriptCore and TinyCC, relinkable from the public sources.
- The phone app hosts the app for other devices as the computer does (owner, 2026-10-16): on Android a listener on every address, port 4580 as the computer's (another if taken, kept), each request answered by the same server code that answers the app's own page — its Host check, client header and cookie session —, media and recordings sent from the files with ranges; Settings → Other devices shows its addresses and QR code. While the app runs a foreground service with a notification keeps it serving when it is put away; closing it from the notification or the recent apps ends it. The phone's Tailscale app has no `tailscale serve`: its tailnet address is plain HTTP (no microphone there, as on any LAN address).
- The speech engines are part of the app (owner, 2026-10-11): `build:cli` builds them, and they are the only runtime files beside the binary rather than embedded.
- Options a request can carry go in each request, not as engine flags: an older engine ignores an unknown field, but an unknown flag stops it.

## Interface

- Words selected anywhere in the app get a small bar by them (owner, 2026-10-15). With an AI model it has one action, Translate: whichever language the words are in, the language learnt is said aloud and the other shown, and the words become a card of the learner's own deck "Finds" by themselves (both faces, their sentence as context; no separate "add" button). The translation shows as soon as the model answers; the words' audio is made after and plays by itself once there (owner, 2026-10-15). Without a model the bar only reads the language learnt aloud. No speaker button on each option: an option's words are selectable instead (a click that selects words chooses nothing).
- Every deck is exported and imported on its own, as one kind of file: a course's words, an imported deck, Finds — each with what was made for its words (audio, examples) (owner, 2026-10-15).
- A calm study tool: content first, large readable target-language text, motion only where it informs.
- No streaks, hearts or other gamification that punishes.
- Nothing moves when an answer is checked or revealed: options keep room for the mark, cards keep their size, and the review buttons share one height.
- An exercise or AI step has one mark everywhere: plan, summary, going over and Notebook (engine `exerciseMark`).
- Check enables only once every item is answered and every recording has been played, and the bar says what it is waiting for. Skip is always available.
- Options are shuffled per pass, seeded by the run, so a repeated lesson cannot be answered by position. The order is stable within a pass. Numeric sequences keep the source order (owner, 2026-10-07).
- All typed gaps of an exercise share one width (in an exam, every gap), so a gap's width never hints at its answer.
- Items and options show no numbers, so nothing resizes as focus moves; number keys still choose (owner, 2026-10-07).
- A checked item shows its result colour on the card's left edge and ✓/✕ on its parts, with the result in words for screen readers. No separate mark (owner, 2026-10-10).
- Review's ratings are coloured buttons with their intervals inside, at the bottom of the screen on phones, as in AnkiDroid (owner, 2026-10-07). A card shows examples one at a time, because all at once was a pile (owner, 2026-10-12).
- The UI never names Anki (it says "deck file (.apkg)"), though review follows Anki's behaviour (owner, 2026-10-11).
- Statistics belong to the Notebook. An exam or course page shows only its latest result and a link there (owner, 2026-10-10).
- Every destructive action asks first and says what goes and what stays.
- Every screen has explicit empty and error states, each with the action that fixes it.
- On phones, action bars and tab rows keep to one row. Each nav label must fit a sixth of 375 px in every language; if not, it gets a `nav.short.*` name.
- Before the learner answers, Understanding says only what kind of text it is ("A voice message"), never what it says.
- Experimental sources stay hidden until switched on, and are presented as an experiment, not exam preparation.
- Content languages are independent of the interface language. Target-language text carries its own `lang` and `dir` (`inLang`).
- The language list names each language in itself, ordered by script as Wikipedia does, with no language favoured.
- Fira Sans is used because one face covers Latin, Cyrillic and Greek, so mixed sentences share a font (Barlow lacked Cyrillic). Other scripts use fallback faces.
- In RTL, text blocks use `unicode-bidi: plaintext`, course HTML and model replies use `dir="auto"`, and titles inside interface lines are isolated (`<bdi>`).
- Answers in the course language (options, chips, gaps) are laid out in that language's direction, not the interface's.
- Some things stay physical on purpose in RTL: a dialog centred by `left-1/2`, Radix popover sides, the play icon's nudge, and media timelines with ←/→ seeking.

## Fixed technical choices

- Bun: runtime, workspaces, `bun test`; the server keeps a Node fallback.
- Hono, with a typed client through Hono RPC (type-only `AppType`); no code generation.
- zod 4 with its built-in `z.toJSONSchema` (`zod-to-json-schema` is deprecated).
- SQLite via `bun:sqlite`, Drizzle ORM and drizzle-kit migrations, WAL.
- The phone app: Tauri 2 (as the desktop), the server's code in its WebView over sql.js (SQLite in WebAssembly, the whole database written back after changes), its files and Whisper (whisper.cpp through a C shim) on the native side. On Android the shared code's files, its requests to other hosts (HttpURLConnection: no CORS, no library added) and Downloads go through a JavascriptInterface (`Native.kt`): the shared code is synchronous where it asks small things. `fzstd` decompresses an .apkg's zstd on the phone (Bun's own on the desktop).
- `ulid` ids, `ts-fsrs` scheduling, `yaml`, `sanitize-html` for importer HTML, `markdown-it` with `html: false`, `country-flag-icons` for flags.
- `pdfjs-dist` (legacy build, in the importer's thread) reads PDFs; PNGs are written with `fflate` (the same bytes on the desktop and the phone). Its bytes differ from those node's zlib made before; a bundle is not refused for such pictures (Library, above).
- The shared code reaches files through course-kit's `DataFs` (Node's on the desktop, the phone app's own), hashes with its own SHA-256 and CRC-32 (`hash.ts`), never `node:*` or Bun outside `runtime/` and `node-fs.ts`.
- DW's HLS fallback (a video whose MP4 is gone) is remuxed in TypeScript (`courses/dw/src/remux.ts`), not by ffmpeg: the same frames as ffmpeg's (decoded, byte for byte), the container laid out a little otherwise — files made before stay as they are.
- `fflate` reads `.apkg`. Profile files and course bundles use our own stored-entry zip (fflate has no ZIP64; a course exceeds 4 GB), profile and deck files read by their checked directory; a course bundle read as it comes, each entry by the size its header gives — never by looking for a signature, which a recording can fake; an entry without its size in its header refused —, the directory checked against every entry read before anything is installed.
- The runtime's own crypto and codecs: WebCrypto (AES-256-GCM, SHA-256; no adapter), `zstdDecompressSync` with capped output, `Database.deserialize` for `.apkg`.
- `pino` once structured logs are needed; `console.error` until then.
- React, Vite, Tailwind, shadcn/ui (Radix), Lucide; native `<video>`/`<audio>`; Motion only when CSS is not enough.
- Fonts bundled, no CDN: Fira Sans (+ Condensed), Latin/Cyrillic/Greek. Barlow and IBM Plex Sans Condensed lack Cyrillic; Sofia Sans sets too small (2026-10-11).
- Other scripts by `unicode-range`: Vazirmatn for Arabic script (46 KB vs Noto's 166 KB), Noto Sans Devanagari. Chinese uses the system font: Noto Sans SC was 4.5 MB and took over Japanese.
- `@dnd-kit/core` for drag and drop; every drag also works by tap.
- `uqr` for QR codes, drawn as our own SVG: `qrcode` has dependencies, `qrcode-generator` is ES5 and gives SVG as a string.
- TanStack Router and Query, React state and context; Zustand only when shared client state outgrows them.
- i18next, react-i18next, i18next-icu; intl-messageformat checks catalogs in tests.
- Charts are our own HTML/CSS; Recharts when charts with axes are needed.
- Native: whisper.cpp, Piper voices through sherpa-onnx, Qwen3-TTS through qwentts.cpp, each pinned; LLMs in LM Studio; Tauri 2 for the desktop shell.
- TypeScript at the current major (`tsc --noEmit` per workspace); no tool may pin an older one.
- Biome; dependency-cruiser with the swc parser (no TypeScript compiler API dependency); Playwright.
- Web component tests: `@testing-library/react` on happy-dom, `bun test --isolate`, run apart from server tests so browser globals never reach them.

## Quality and testing

- TypeScript `strict` with `noUncheckedIndexedAccess`; no `any` without a comment saying why.
- The fixture course `courses/_fixture` must hold an exercise of every type, validate, and match its fingerprints; a missing type fails CI.
- e2e never uses a real model: AI screens run against a fake OpenAI-compatible server; decks are synthetic `.apkg` files.
- Real-course run-throughs and speech checks use an APFS clone in a throwaway data root, never the owner's profiles; they assert on structure, never course text; Mac only, not CI.
- Speech round-trip bar: a median of 85% of words heard per language pair. `speech:levels` fails when an answer is missed or noise is heard as words.
- The CLAUDE.md path check covers backticked paths starting `packages/ apps/ courses/ native/ docs/ e2e/` and `## Layout` trees; "(planned)" lines and `<placeholders>` are skipped.
- A commit body says the problem, the modules, why this place, what was reused and what was deliberately not built.
